## Goal
Every `GameEvent` carries `tick` (events/README.md), but nothing in `core` knows the current tick number. `core.tick` advances a persisted counter, and command handlers, system ticks and event handlers read it from their context, so systems fill `tick` without inventing their own clock.

## Definition of done
- [ ] A singleton table (e.g. `world_clock`, one row) holds the current tick number; `tick()` increments it once per call, before running systems
- [ ] `CommandContext`, `EventContext` and `TickContext` expose the current tick number (read once per step, not per event)
- [ ] Tests: the counter starts at 0 on a fresh store, increments once per `tick()`, and a command executed between ticks sees the last tick's number
- [ ] `pnpm build`, `pnpm lint`, `pnpm test` green locally
- [ ] Reviewer checks: no file over 600 lines, no numeric literal other than 0/1/-1 in `rules.ts`/`tick.ts`, no store scan, nothing imported from `server`/`client`

## Notes
Found while building P0-006: the kernel dispatches events but the P0-006 DoD gives it no tick number to hand out. P0-008 emits `entity.sector_changed` and needs this (or it stamps `tick: 0`). The replay script format (P0-017) counts ticks on the host side; this counter should agree with it.
