## Goal
`pnpm server:down` + `pnpm server:up` keeps every identity valid. Today the
local SpacetimeDB generates its JWT signing key at `/root/.config/spacetime/id_ecdsa`
inside the container, not in the `bastion-stdb` volume, so recreating the
container (every `server:down`) invalidates every browser token and the CLI's
own login (`pnpm server:publish` then fails with `InvalidSignature` until
`pnpm server:cli logout`). Keep the key pair under `/stdb` so only removing the
volume changes it, as the README already claims.

## Definition of done
- [ ] `docker-compose.yml` (and `scripts/up.sh` if key generation is needed) keeps the JWT key pair in the `bastion-stdb` volume, e.g. via `spacetime start --jwt-pub-key-path/--jwt-priv-key-path` under `/stdb`, or by mounting the config dir from the volume
- [ ] Manual check recorded in the PR: `pnpm server:up`, publish, `pnpm server:down`, `pnpm server:up`, then `pnpm server:publish` succeeds without `server:cli logout` and a browser tab reconnects as the same identity
- [ ] README Troubleshooting "Stale auth token" matches the new behaviour (only a volume wipe changes the key)
- [ ] `pnpm build lint test tasks:validate` green

## Notes
Found while proving P0-042 against a local server: a plain `server:down` /
`server:up` with the volume intact produced `Failed to verify token:
Unauthorized` in the browser. `docker exec bastion-spacetimedb-1 ls
/root/.config/spacetime` shows `id_ecdsa` and `id_ecdsa.pub` outside the
`/stdb` mount. Since P0-042 the browser recovers on its own (fresh identity),
so this is about keeping identities across restarts and the CLI login, not a
stuck client.
