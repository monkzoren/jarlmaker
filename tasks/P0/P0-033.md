## Goal
`tools/contentlint`'s tests pass whether or not core registers the `movement`
and `world` tuning sections, so P0-029 (which makes importing `@bastion/core`
always register them) can merge with `pnpm test` green, and later systems
registering more sections do not break these tests again.

## Definition of done
- [x] `test/lint.test.ts` builds its inline content sets on top of the real content (`content` from `@bastion/content`, e.g. `{ ...content, tuning: { ...content.tuning, lintFixture: … } }`) so every section core registers is present and valid
- [x] `test/fixtures/broken.ts` keeps exactly two problems (a function value and an invalid `lintFixture` knob) and otherwise supplies valid values for every registered section; the function lives under a section other than `world` (or alongside valid `world` keys) so `tuning.world.sectorSize` does not become a third error
- [x] Error assertions still pin the exact two error paths; the "unregistered section" test asserts `tuning.net`'s warning with `toContain` rather than an exact list
- [x] Verified in both states: `pnpm --filter @bastion/contentlint test` green on `main` and green with P0-029's branch (`task/P0-029`) merged in locally
- [x] `pnpm build lint test tasks:validate` green

## Notes
Done by the integrator in PR #22 together with P0-029 (a test-data-only fix on the critical path). The "unregistered section" test asserts its own `unregisteredFixture` section with `toContain` rather than `tuning.net`, so it keeps passing when `net` gets a schema.

Discovered while working on P0-029. Once `packages/core/src/index.ts`
re-exports `entity`, `movement` and `world` are required tuning sections, and
the hand-built sets in `lint.test.ts` / `fixtures/broken.ts` fail with
`tuning.movement: Invalid input: expected object, received undefined` and
`tuning.world.sectorSize: ... received undefined`. P0-029 depends on this.
