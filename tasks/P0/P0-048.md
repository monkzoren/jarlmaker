## Goal
ADR 0008 and CLAUDE.md 3.6 rule 7 describe the movement freeze as P0-046 built it. The freeze now starts after `tuning.net.offlineMoveGraceMs` with no server traffic, whether or not the client has declared a drop yet. Traffic resuming on the same link unfreezes it and sends the current stick once. P0-046 also lowered the grace from 500 ms to 300 ms. The ADR still says the freeze starts "once the client detects a drop" and quotes "~0.5 s".

## Definition of done
- [ ] `docs/DECISIONS/0008-movement-freezes-offline.md` gains an "Amended by P0-046" note. It says the grace counts from the last server traffic (or a detected drop) and names `tuning.net.offlineMoveGraceMs` (300 ms) instead of "~0.5 s". It also says that traffic resuming without a drop resyncs and sends the current stick once.
- [ ] The trade-off is written down in the ADR's Consequences: a live link silent for longer than the grace freezes the sprite briefly, then it catches up.
- [ ] CLAUDE.md 3.6 rule 7 says movement freezes "after a short grace period with no server traffic" (not only "while dropped")
- [ ] `pnpm build lint test tasks:validate` green

## Notes
Discovered while working on P0-046, whose `touches` do not include `docs/DECISIONS/` or CLAUDE.md. Why 300 ms: the P0-046 DoD asks for ≤ 0.6 cell of drift when a key goes down 200 ms after the cut. Walking speed is 4 cells/s, and the last `world_clock` update lands up to 100 ms before the cut. So a 500 ms grace walks 0.55 to 0.95 cells, and the smoke run measured 0.72. A grace of 400 ms or less is needed; 300 ms keeps a margin.
