## Goal
Movement behaves as ADR 0008 decides. When the connection drops, the player's own movement stops after a short grace period instead of predicting a walk the server will never see. Offline stick changes are discarded, and on reconnect the client sends its current stick once. Non-movement commands keep queuing as before. There is no snap-back after a tunnel.

## Definition of done
- [ ] After a drop is detected, local prediction for the own player stops after `tuning.net.offlineMoveGraceMs` (new knob, core schema + content value ~500, intent comment). Remote entities also hold still.
- [ ] `entity.move` commands issued while dropped are not queued. On reconnect, one `move` with the current stick (with a fresh nonce) is sent after the queued non-movement commands.
- [ ] Unit tests over the fake transport: press-and-release while offline sends nothing, and after reconnect the drawn position equals the server position (no correction offset). Holding a key across the reconnect resumes walking from the server position. A non-movement command queued offline still replays.
- [ ] New smoke scenario `offline-tap`: walk, cut the socket, press and release a direction while offline, restore. It asserts the server position is unchanged by the offline tap and that the client's drawn position matches the server within 0.1 cell 1 s after reconnect. The existing `walk-and-drop` still passes.
- [ ] Reproduced first: the PR shows `offline-tap` failing on `main` before the fix
- [ ] `pnpm build lint test contentlint replay smoke tasks:validate` green; if the replay content hash moves, `pnpm replay --update` changes only the hash

## Notes
Filed by the integrator after screenshots showed the snap-back: 1 s of offline walking left the server's `entity_pos` unchanged. The cause is that stick-state commands replayed back to back collapse to a zero-length press. Decision and alternatives are in `docs/DECISIONS/0008-movement-freezes-offline.md`. It depends on P0-041/P0-042 (same files, same lane).
