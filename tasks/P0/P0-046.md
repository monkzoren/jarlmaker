## Goal
ADR 0008 holds for real tunnels, not only for drops the client has already detected. The client needs about 3 s of server silence before it declares a drop. P0-043 starts the movement freeze only after that, so keys pressed in the first ~3 s of a tunnel still walk the Viking locally, then snap back. The freeze must start after `offlineMoveGraceMs` of server silence. The server's clock updates every tick, so this is 100 ms granularity. The worst case then becomes a snap of under ~0.5 s of walking.

## Definition of done
- [ ] Own-player prediction freezes once there has been no server traffic (any subscribed update, including `world_clock`) for `tuning.net.offlineMoveGraceMs`, whether or not the reconnector has declared a drop yet. Prediction resumes on the next server update.
- [ ] Moves issued while frozen are not sent. When traffic resumes, the client sends its current stick once (same rule as after a reconnect).
- [ ] Unit test over the fake transport: the server goes silent, a key is pressed 200 ms later and released after 600 ms, and the connection resumes after 5 s. Drawn drift while silent is at most `offlineMoveGraceMs` worth of walking, and after resume drawn == server.
- [ ] Smoke `offline-tap` gains a variant (or a second scenario) that presses the key 200 ms after the socket is cut, which is before drop detection. It asserts max drift ≤ 0.6 cell and snap-back ≤ 0.6 cell. PR shows it failing on `main` first.
- [ ] `pnpm build lint test contentlint replay smoke tasks:validate` green
